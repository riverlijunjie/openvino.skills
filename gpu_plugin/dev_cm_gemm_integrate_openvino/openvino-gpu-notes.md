## CM GGUF GEMM (fc_gguf_cm.cpp/.hpp, gemm_q{4k,5k,6k,40,41,80}_full.cm): fused-op dtype bug (found after 2 sessions of chasing the wrong hypothesis)
- Symptom: Q4_1 (and potentially other GGUF quant) end-to-end generation produced all `!` tokens. Two full sessions were spent assuming the *primary activation input* (INPUT 0) was fp32 for some FC nodes ("*_decompressed_to_f32") and building f32->f16 input-conversion logic. That hypothesis was WRONG.
- Ground truth (confirmed via `OV_VERBOSE=4` `calc_output_layouts` logs): the FC node's own activation input stayed fp16 the whole time (e.g. `f16:bfyx:2048x1x4096`). Only the node's OWN OUTPUT was fp32 (`f32:bfyx:?x1x4096`), AND a **fused eltwise Add's outer-dependency** was fp32 (a residual add feeding into an fp32-precision downstream RMS-norm path).
- Real root cause: in `FCGGUFCmGemmGenerator::get_jit_constants()`, `CM_POST_OPS_DECLS` hardcoded every fused outer-dep pointer as `half* cm_post_inN` ("Fused binary inputs to GGUF FCs are fp16 (same type as the output)" — false assumption). When the actual fused Add operand was fp32, the CM kernel read half the bytes as garbage half values -> silently corrupted every fused-add output -> cascaded into all-`!` generation. The OCL shuffle-GEMV decode path was NOT affected (it uses the standard cldnn FUSED_OPS jitter which correctly reads dtype via `make_type_jit_constants`), which is why forcing fp32-output nodes onto the OCL path "fixed" the symptom in one experiment (but that was masking the CM bug, not fixing it, and other correctness issues (dyn_quan disabled for dynamic weight zp) remained on OCL).
- Fix: track each fused op's actual `outer_dep_start_idx` layout dtype via `params.input_layouts[fd.outer_dep_start_idx].data_type` (this is the correct/established way to get a fused outer-dep's dtype — same pattern used in `kernel_selector_helper.h`/`fully_connected.cpp`), and declare `cm_post_inN` as `float*` or `half*` accordingly in `CM_POST_OPS_DECLS`. The apply-statement casts (`(float)cm_post_inN[out_idx]`) already work correctly for either declared type, no change needed there.
- Lesson: when a GGUF FC node has a *_decompressed_to_f32 fused chain, do NOT assume only the primary activation/output dtypes matter — always check the dtype of every fused outer-dep too (`params.fused_desc[i].outer_dep_start_idx` -> `params.input_layouts[idx].data_type`). `calc_output_layouts` debug lines print ALL input tensors (including fused deps) in order, followed by the output tensor — count them carefully; a node can have 3 "input tensor:" lines (activation, weight, dummy scale placeholder) in one shape-inference pass and 4 (with the extra fused fp32 add operand) in another.
- Design actually implemented per user request (kept, working): CM GEMM output supports fp16/fp32 directly via `CM_OUTPUT_F32` JIT (`cm_output_t`/`cm_ptr_store<float,...>` vs `cm_ptr_store<uint,...>`), and CM GEMM activation input supports fp32 via a separate tiny pre-pass kernel `convert_act_f32_to_f16.cm` (flat, 64 elements/thread, threads=ceil(M*K/64)) that converts fp32 activation -> a scratch fp16 buffer (grow-only, per-impl-instance `cldnn::memory::ptr`, allocated via `engine.allocate_memory(...)`/`stream.finish()` before growing) BEFORE dispatching the big GEMM kernel; `FCGGUFCmImpl::get_arguments()` swaps in the scratch buffer instead of the raw fp32 dep memory only for the GEMM stage's INPUT(0). The big GEMM kernels (`gemm_q*_full.cm`) never need a second input ABI — this proved unnecessary for the actual failing case (activation was always f16) but is still correct defensive support per the design request.
- CM `cm_ptr_load<float, N>`/`cm_ptr_store<T,N>` only accept certain "vector sizes" for LSC block load/store (256 elements is NOT valid -> `static_assert ... "invalid vector size"`; 64 works fine). Keep per-thread block sizes at 64 or smaller for flat float loads.
- Adding a new `.cm` file requires re-running `cmake -S <src> -B <build-dir>` (not just `cmake --build`) because `src/plugins/intel_gpu/src/graph/impls/cm/CMakeLists.txt` uses `file(GLOB_RECURSE KERNELS ...)` which is evaluated at configure time only.
- For syncing optimized standalone `gemm_q40_full.cm`/`gemm_q41_full.cm` into plugin kernels, keep plugin-only ABI/JIT hooks (`cm_output_t`, `CM_OUTPUT_F32`, `CM_POST_OPS_DECLS`, optional `CM_INPUT_F32`) and only merge hot-loop optimizations. Q4_1 layout must stay `weights = pqs_T || pd_T || pm_T` (separate SoA `pd`/`pm`, not interleaved `pdm`).
