## 3. 计时协议与事件映射

`cl.profiling(True)` 单个 in-order queue。所有 GPU tensor、JIT、history、元数据、scratch 和 cache-flush buffer 均在计时外创建。

每个缓存协议先 100 次完整 `p.enqueue(); cl.finish()` 预热，再 20 次采样。
cold96MiB 每次采样前读写 96 MiB buffer 并单独 `finish()`，**flush 不包含在 host 或 GPU 时间中，也不插入阶段之间**。
预热本身不逐次 flush。no-flush 不主动驱逐缓存；不等同于所有访问必然 cache hit。

- host：`perf_counter_ns()` 包住一次完整 `p.enqueue()` 到 `cl.finish()` 返回，包括 Python/OpenCL 提交、同步和事件收集成本，不含数据上传/读回。
- GPU sum：完整 slice 中所有 kernel event duration 的和；**不是首 event 开始到末 event 结束的跨度**，因此不包含 event 间空隙。无阶段间同步。
- 同一 Q2 阶段跨多个 chunk 的 event，先在每个 sample 内求和，再计算该阶段 mean/median/p95。整体 p95 也从每个 slice 的 sum 计算，不能把各阶段 p95 相加。
- p95 使用 `np.percentile(samples, 95)` 默认线性插值，20 样本统计，不是长期尾延迟保证。
- 每种协议采样后，全量 payload/guard 与计时前验证快照逐元素精确比较。

事件顺序（0-based，C 为 score chunk 数）：

1. event 0：`Q0` → `qsa_kv_cache_update`。
2. event 1：`Q1-project` → `qsa_project_dpas`；event 2：`Q1-prepare` → `qsa_prepare_projected`。
3. 对 chunk j：event `3+2*j` 是 score，event `4+2*j` 是 finalizer；每块 score 全部历史列，然后 finalize 写全局 selected/count，再复用同一个 scratch。
4. prefill：event `3+2*C` 是 `Q3-gqa-W4`，总 `4+2*C` events。
5. decode 1024：Q3 scalar，6 events；decode ≥2048：Q3 split-P16 producer + reduce，7 events，表中 Q3 total 包括两者。

prefill score 使用 DPAS；全 dense 1K/2K 的 finalizer 为 WG8；≥4K 使用原有 scalar finalizer。decode score 为 partition16，finalizer WG16；1024/2048 的 score 是 dense bypass 空工作 dispatch，仍计入事件成本。

## 7. 验证方法、计数和误差

顺序是：实际完整管线 → full readback/guard → streamed Q1 oracle → 逐 score chunk 重算/检查 → sampled main attention → 完整 replay 精确比较 → 预热/计时 → post-benchmark 精确比较。
重算 score 仅为计时外验证，不改变保存的首次完整管线 selected/count/out。

- Q0：全部当前 K/V 写入精确，所有未触及 cache 位精确不变。
- Q1：每 1024 行 NumPy FP32 projection，验证**全部** projection、iq、raw 和新 summary；fresh raw 的 pooling 在 FP32 累加后转换，未用 half raw 替代原语义。
- Q2：所有 count、selected、padding 精确检查。每个 sparse row 对实际 GPU 自有 score 执行完整候选 lexsort（score 降序，ID tie-break 升序，最终按 ID 排序），与 finalizer 输出精确比较；dense 行检查 bypass 和自然顺序。每次只保留有界 score scratch 的快照，不保留完整 NT×MB 主机矩阵。
- NumPy score 为**采样**：32 个均匀行，加 chunk 两侧、最后行、dense/sparse 2047..2055 边界；只统计其中 sparse 行。并非对全部 64K×16K scores 做 NumPy GEMM。
- Q3：同一组选定行，使用实际 selected/KV 的 NumPy FP32 主 attention，包括 sigmoid gate。不是 full-ref 64K，也不是模型质量/原 scalar 管线 bitwise 等价声明。
- 所有实际 out/iq 元素均做有限检查，split acc/ml 也全部有限；所有 Buffer guard、score guard、未使用 score 行、完整 replay、每个缓存协议后的所有 payload 比较均通过。
- tolerance：projection atol=3e-5/rtol=2e-5；Q1 half outputs atol=8e-3/rtol=2e-3；score atol=3e-5/rtol=2e-5；Q3 atol=rtol=2e-3。没有修改这些既有容差。

## 9. 后续 roofline 的精确逻辑工作量输入

本报告**不把逻辑工作量推导成未经审计的硬件利用率**。`WORK` JSON 可作为后续 roofline 输入，定义：

- `nc(t)=(abs_pos(t)+1)//4`，dense 为 `nc<=512`；sparse candidates 仅累加非 dense 行的 nc。
- selected blocks=`min(nc,512)`；tail=`(abs_pos+1)%4`；attended positions=`4*selected+tail`。
- Q1 projection FLOP=`2*q*2560*640`；Q2 useful dot FLOP=`2*4*128*sparse_candidates_sum`（dense bypass 排除）。
- Q3 useful QK+PV FLOP=`2*24*(256+256)*attended_positions_sum`，不含 softmax、gate、归一化等；GQA DPAS padding/块对齐导致的实际指令工作不应混同于 useful FLOP。
- Q0 输入+输出 essential bytes=`4096*q`；Q1 projection FP32 scratch 写+读逻辑字节=`2*q*640*4`，必须在逐阶段模型中计入，不能直接沿用旧 scalar Q1 bytes。

## 11. 限制与完整性

- 所有尺寸是实际测量，不是 roofline、拟合或外推；没有算整体模型 token/s，也没有插件/部署或模型质量结论。
- 只有一个 seed 和每协议 20 个稳态样本；no-flush 在 cold 后运行，未做跨协议顺序平衡，故微小差异不作因果解释。
- 完整 GPU slice 的定义不含历史、CPU reference、tensor 构造/JIT、flush、上传/下载，也不含真实模型中产生 x/Q/K/V 的上游算子。
- 独立新增脚本的 Q1 streaming oracle 仅支持本次 B1、r 对齐 past、q 为 r 倍数或 1 的形状；未替代通用 edge/mixed-batch validator。本次没有重跑无关的全部旧回归套件。
- 基于日志复核 28 组、560 个 event sample 向量；每向量长度与事件映射一致，stage mean 总和与 GPU mean 一致，20 个逐 slice 原始和复算一致，全部源哈希一致。每阶段 median/p95 和原始逐 event 数据均在 `BENCH.stages` / `event_samples_ms`，不是估计值。
